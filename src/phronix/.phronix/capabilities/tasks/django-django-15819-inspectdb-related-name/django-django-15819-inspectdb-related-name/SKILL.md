## Instructions

### I1 — Problem

When `inspectdb` generates models from a database that has self-referential (same-entity) relations — where a table references itself — it doesn't generate `related_name` attributes for the ForeignKey/OneToOneField fields. This causes Django's E304 error: "Reverse accessor for 'module.Model.field1' clashes with reverse accessor for 'module.Model.field2'." The fix ensures that when `rel_to == "self"` (i.e., the relationship points back to the same table), a unique `related_name` is automatically generated.

### I2 — Key Idea

The related_name 'attribute_name' must be autogenerated for all self-referential fields in the generated model to prevent E304 reverse accessor clashes. The "email field is not always called 'email" — inspectdb must autogenerate related_name based on the already-normalized att_name variable.

### I3 — Instructions to Solve It

File: `django/core/management/commands/inspectdb.py`, lines 185-188
When `rel_to == "self"`, add `extra_params["related_name"] = att_name`.
The `att_name` variable is already correctly available from the `normalize_col_name()` call at lines 144-146, and it's already tracked in `used_column_names` for uniqueness across multiple fields.

### I4 — Constraints and Rules

- Only add `related_name` when `rel_to == "self"` — do NOT add it for non-self-referential relations (the `if rel_to in known_models:` block at line 189 already handles those separately)
- The `att_name` variable comes from `self.normalize_col_name(column_name, used_column_names, is_relation)` — it is already normalized for Python compatibility (lowercased, `_id` stripped, unsuitable characters replaced, Python reserved words handled by appending `_field`, and name conflicts resolved via `used_column_names` tracking with `_1, _2` suffixes)
- Do NOT use the undefined `new_name` variable — always use `att_name`
- The fix must not break any existing tests: test_same_relations, test_attribute_name_not_python_keyword, test_stealth_table_name_filter_option, test_table_option

### I5 — Pitfalls and Lessons

- Using `new_name` instead of `att_name` causes `NameError: name 'new_name' is not defined` (happened in attempt 2)
- The fix at lines 185-188 must be precise: only add `related_name` when `rel_to == "self"`, not unconditionally
- All four previously failing tests now pass with the correct fix: test_same_relations, test_attribute_name_not_python_keyword, test_stealth_table_name_filter_option, test_table_option
- The fix verified: adding `related_name=att_name` only when `rel_to == "self"` prevents E304 clashes
- Self-referential ForeignKey/OneToOneField fields get a unique related_name preventing E304 clashes
