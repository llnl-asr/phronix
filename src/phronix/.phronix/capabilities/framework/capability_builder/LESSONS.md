# Lessons: capability_builder

- [L-148dcf38] A capability_builder background agent can be stopped by a session end before it stages its proposal: after the user said "done restarted" and "done approve", capability_list showed no pending proposal for repro_package (v10, no output_root in repro_verify). Before telling the user to approve, check capability_list pending for the proposal id, and resume the agent with SendMessage if it is missing. prov_annotate (v13) and workload_elmerfold (v1) were applied by the user's earlier approvals.

- [L-3c35680e] A capability_builder agent was stopped by a session restart twice while staging a whole-file tool_code change for repro_package (116 KB tool.py); user said "continue". To survive restarts, stage in order: first a small capability_update (why + skill_md only) so a proposal exists, then capability_refine it with the large tool_code, then capability_verify; report the proposal id as soon as the first step exists.

- [L-f02b6e0e] The staged-in-order approach worked partly: after restarts the small skill_md proposal for repro_package was applied (v11, rule 'verification never on home' in SKILL.md) but the tool_code step was not staged, so the rule is live while repro_verify still has no output_root. Check tool.py (grep the new parameter) and not only the version number before telling the user a fix is done.

- [L-08e082a0] capability_update proposals are rejected when test code holds literal machine paths (e.g. an /g/g92 or /p/lustre5/u path in a unit check: "machine-specific path ... take paths as arguments"); build such strings from constants (HOME_FS + "/g92/x", LUSTRE_BASE + "/u/x"). capability_refine cannot carry checks, so a change that adds a check needs a full capability_update (tool_code + checks); omit skill_md when the skill is already staged/active.

- [L-282acacd] The third resume of the repro_package tool_code builder succeeded (proposal bba3adeb8a7d, capability_verify clean, 7 checks pass) after the first two were stopped by restarts: when a builder agent is stopped, resume it with a narrowed brief and the current facts (here: the user had removed ~/moirai_repro, so add outputs_gone and a fresh-batch path). The test code must not contain literal site paths (validation refuses them): build them from parts.

- [L-4805ba41] When the user reports a proposal out of date (repro_package at v12 after the earlier approval), read the current tool.py and diff what is already live (grep the new names), then refine on_current with only the missing parts: here outputs_gone and a self-test fix. This produced proposal 268732cd4881 with 7 of 7 checks and kept every v12 addition.

- [L-6a305cdc] User: "No it should have the new validator." The TraceViewer-count change for repro_package (row_counts) never reached tools: grep of capabilities/repro_package shows it only in LESSONS.md, versions are v8/v9. Builder agents on whole-file capability_update changes of a ~120 KB tool.py (capability_get result 222 KB, too large to read) were stopped twice by session/MCP restarts before staging (L-148dcf38, L-3c35680e). Before telling the user a change is live, grep the live tool.py for it; for a change of a few lines in a big tool, capability_update still takes the whole tool_code, so ask whether a direct small file edit is allowed or ask the user not to restart while the builder runs. Capability needed: capability_update with a patch/diff argument (old_string/new_string) instead of the whole tool_code.

- [L-b1e1bac7] Proposal 08ef4a3c5a41 (prov_performance) went out of date because the earlier Python-only proposal b8ddd4679005 was approved first (prov_performance v2: perf_annotate, perf_preview, perf_apply, perf_validate, perf_diagram, perf_annotate_selftest live). When several proposals of one capability are staged, the user approves the one they see first: refine the later ones on_current right after the first is applied, and keep the superseded ones marked so the user does not approve both. The remaining part of 08ef4a3c5a41 is the clang model for C/C++ (extract_functions, R6/R7, threshold 20), C++ insertion and the full skill and checks.

- [L-cc2ec2c8] Staging order worked for the 120 KB repro_package tool.py: skill-only capability_update first (id 29ec1f862aa3), then capability_refine with the whole tool_code. A refine whose sandbox check fails stages nothing (nothing is kept), so the whole text must be resent: write the selftest fixtures with values that cannot overlap (a fake user 'tester' matched '/tester/' inside the fake home '/home-fake/tester', giving two findings instead of one). Final refine id d3fb897f86ea verified clean.

- [L-f4395a2e] Stale proposal (tools_moirai_venv): proposal 268e2994a8b4 went out of date because the capability moved to v3 (already installing dftracer[modules] and composing) and its SKILL.md changed after staging; approving would undo the newer version. Recipe that worked: (1) capability_get the current version and compare the proposal's "why" with it; (2) redo only the missing delta, using capability_refine on_current=true and sending the whole tool_code and skill_md of the current version (staged as new proposal f89e80dd73a3, applied as v4); (3) then ask the user. Delta here: venv cmake>=3.24 first on PATH for dftracer-compose, import test at the end of the script, libstdc++ preload corner case plus corrector row, keeping v3's --enable mpi,hdf5 --disable papi,hwloc,hip,cuda. After the refine the old proposal is superseded ("already refined"): capability_reject on it errors and it cannot be refined again, so only apply the new id. Check the capability's current version before staging a capability_update so it does not go stale.

- [L-81607df2] Where a capability lives -> each project keeps the capabilities of its subject in its own repo (phronix: workloads, software, systems, tooling, process; dftracer-agents: dftracer_*; moirai-agents: provenance; rabbit-agent: Rabbits), decided by phronix.engine.scopes.owner (the package its code imports, else its name prefix, else phronix) -> a change to another project's capability goes to that project as a commit on contrib/<project> in vendor/contrib/<upstream>, which a person pushes as a pull request; the shared store agent-capabilities is retired (2026-11-13)

- [L-a950f26e] Builder agent resumed for tools_nextflow_annotate (taxteller) found capability_list, capability_get, capability_new, capability_verify and lesson_add all returning "No such tool available" (the moirai MCP server answered as connected but had dropped its capability tools; a ToolSearch for capability_new found nothing). It correctly stopped and staged nothing. Rule: do not retry blindly, do not send the whole tool_code blind (a failed check stages nothing) and do not work around by hand-editing the store; say nothing was applied, check first whether tools_nextflow_annotate is already staged (capability_list after reconnect, to avoid a duplicate), and ask the user to restart or reconnect the moirai MCP server (the running server keeps its state; see dftracer_admin), then resume the same build. The entity diagram question ("where is the entity diagram?") stays open until annotate_diagram/diagram_publish_graph can run.

- [L-fabbb1d7] A tool argument typed str that carries a numeric-looking id (Slurm job id 319353) arrives from the MCP call as an int: coerce with str(x).strip() in the tool before any string method, and add a selftest or check that passes an int. app_smoke ded8109f29de crashed in smoke_validate with "'int' object has no attribute 'strip'" right after the user's approval, so a second proposal (5bcd4eab394b) and a second yes were needed.

- [L-6ea52ef7] Where capability code lives: the live source is src/moirai_agents/.agents/capabilities/<name>/tool.py (with versions/vN/), not workspace/.moirai-agents/capabilities (does not exist) and not build/lib. In the taxteller smoke-approval turn the agent lost 3 calls searching; use capability_get or open the src path directly before capability_update. Also, after a user approves a gate whose validator cannot judge the run, pipeline_decide succeeds but pipeline_advance still errors "validator verdict is fail": fix the validator via capability_update (proposal) and say the stage stays open until the user applies it.

- [L-a3bf5db8] Staging a long tool (tools_nextflow_annotate, about 600 lines) took two steps and survived a session interruption only because each step was reported: skill-only stub proposal first (ab4a027d09d8, superseded), then the whole-tool refine (7682bc6b1158, verify: no problems, selftest 20 of 20). After the builder reports, ask one question that names the proposal to apply and the superseded one to reject, so the user is never asked to approve both.

- [L-c97cdfd7] Staging a large new capability worked in two steps (tools_nextflow_annotate): a skill plus a stub tool with the final tool names and 'raises' checks (proposal ab4a027d09d8), then capability_refine with the whole tool_code (7682bc6b1158, 20 of 20 selftest fixtures). capability_new refuses a skill whose Self-learn lacks the words 'becomes a capability' and an agent.json whose skills omit the capability's own name; put the selftest inside the tool (selftest check) so the sandbox runs every fixture while the checks list stays small.
