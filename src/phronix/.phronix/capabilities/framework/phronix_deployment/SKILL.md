## Instructions

### I1 — Deploy into the project

```
phronix deploy            # idempotent: writes only what differs
phronix deploy --check    # writes nothing; exits non-zero if out of date
```

Re-running is a no-op that says so. Use `--check` as a CI gate to catch a
workspace that has drifted from the installed package.

### I2 — Start the stack

```
phronix_stack start       # deploy, then mlflow + collector + mcp server
eval "$(phronix_stack env)" && claude
```

`start` doubles as `refresh`: it compares each running daemon against the
configuration and bounces only what actually changed.

### I3 — Know what deploy produces

| Path | What it is |
|---|---|
| `.phronix/` | the project's knowledge layer — **commit this** |
| `.claude/agents/`, `.opencode/agents/`, `.github/agents/`, `.codex/agents/` | rendered agents (gitignored build artifacts) |
| `.claude/skills/`, `.opencode/skills/` | symlinks into the merged skill store |
| `.claude/settings.json`, `.opencode/opencode.jsonc` | rendered permission blocks |
| `.claude/hooks/`, `.codex/hooks.json`, `.opencode/plugin/` | prompt-injection wiring |
| `.mcp.json`, `.vscode/mcp.json`, `.codex/config.toml` | MCP server registration |
| `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md` | a managed block inside your own file |

### I4 — Diagnose a stale workspace

`phronix deploy --check` names exactly what drifted. Then `phronix deploy` to
repair. If a file is reported as a conflict rather than updated, it exists and
was not generated by phronix — deploy will never overwrite it.

## Rules

### R1 — Deploy is additive and never destroys your content

Instruction files get a delimited block inserted or refreshed; the rest of the
file is untouched. A file that collides with a generated name but was not
generated by phronix is reported as a conflict and left exactly as it is.

### R2 — Commit `.phronix/`; do not commit the rendered artifacts

`.phronix/` is the knowledge the next clone inherits. The per-harness agent files
and skill symlinks are regenerated from it, and committing them produces a diff
on every model-map change for files nobody edits.

### R3 — A healthy collector is never bounced by `start`

Its profile is in memory. `start` leaves it alone even when its configuration has
drifted; use `restart` when you genuinely mean to lose the accounting.

### R4 — Daemons self-limit their lifetime

Every one is started under a `PHRONIX_STACK_MAX_AGE` deadline (default 8h) so a
forgotten `stop` cannot leave a process running for days on a shared machine. Set
it to 0 for a session that must outlive that.

## Constraints

- Never edit a rendered agent or permission file; change the source and redeploy (P1).
- Never commit the rendered artifacts; commit .phronix/ (R2).
- Deploy never overwrites a file it did not generate (R1).

## Corner cases

- What deploy produces (I3): .phronix/ (knowledge layer, commit); .claude/agents, .opencode/agents, .github/agents, .codex/agents (rendered, gitignored); .claude/skills, .opencode/skills (symlinks into the merged store); .claude/settings.json, .opencode/opencode.jsonc (permission blocks); .claude/hooks, .codex/hooks.json, .opencode/plugin (prompt-injection wiring); .mcp.json, .vscode/mcp.json, .codex/config.toml (MCP registration); CLAUDE.md, AGENTS.md, .github/copilot-instructions.md (a managed block inside your own file).
- start compares each running daemon with the configuration and bounces only what changed, except a healthy collector (R3).
- P1 (source pitfall) — Editing a rendered agent or permission file: Both are regenerated. The change survives until the next deploy or sync, which is long enough to look like it worked and short enough to be baffling when it stops.
- P2 (source pitfall) — Expecting `--check` to cover the harness memory symlink: It deliberately does not. That link points into `~/.claude/projects/<slug>/`, keyed on the project's absolute path, so a scratch comparison can never reproduce it — including it would report drift forever on an up-to-date tree.
- P3 (source pitfall) — Assuming a port is the configured one: When the configured port is held by another process the stack takes a free one and persists it. Read the port from `phronix_stack status` or `env`, not from the configuration.

## Parallel plan

Independent calls go out together in one message: predictor calls on different inputs, and lookups such as knowledge_search or lesson_search, do not depend on each other. Sequential, and why: the validator runs after the predictor whose result it rules on, and the corrector only after the validator's verdict. Larger fan-outs build on [[tools_parallel]] (parallel_plan / parallel_call / parallel_validate).

## Corrector

- Predictor `phronix_deployment_plan`, validator `phronix_deployment_check`. A failed verdict comes here: repair the record (or the step that produced it), then plan and validate again. The same failure twice stops the loop: change approach, or ask the user.
- `project_named` failed: name the project root deployed into
- `deploy_ran` failed: run phronix deploy (or --check in CI) and record its result
- `conflicts_untouched` failed: restore the conflicting file: deploy never overwrites a file it did not generate (R1)
- `no_rendered_commits` failed: commit .phronix/ only; rendered agents, skill symlinks and permission/MCP files are regenerated (R2)
- `port_from_status` failed: read the port from phronix_stack status or env, not from the configuration (P3)
- `collector_kept` failed: use start (which leaves a healthy collector alone) unless you mean to lose the accounting with restart (R3)
- `goal is required` from the planner: restate the concrete target (the task, file, run or stage) and plan again.
- A check that is wrong about a correct record: reproduce it with a new entry in checks.json and `capability_update` this capability; never loosen the record to pass.

## Self-heal

- A stale workspace: deploy --check names the drift, deploy repairs it (I4).
- A tool here failed or ruled wrongly: follow `capability_builder`'s Self-heal (reproduce with a check, `capability_update`, user approval) rather than working around it.

## Self-learn

- What is explored while applying this procedure (a new workload, software, tool, system or way of doing it) becomes a capability: see capability_builder (Rules).
- A new harness path that deploy should produce is a change to the deployer, recorded as a lesson here.
- A new pitfall of this procedure: `lesson_add` it to this capability with its evidence (a run, a log line, the user's words).
